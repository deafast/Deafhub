## Схема

Текущая hosted Supabase сверена только чтением с изолированной PostgreSQL, восстановленной из db/competition.sql, db/tournament-engine.sql, db/tournament-operations.sql и четырёх миграций бронзы/FC/истории. Совпали 220 структурных записей: таблицы и права чтения/записи, RLS, столбцы/nullable/default, PK/FK/UNIQUE/CHECK, политики, триггеры, контрольные суммы тел hub-функций, SECURITY DEFINER/search_path и EXECUTE для anon/authenticated/service_role. NOT NULL сравнивается через свойства столбцов, а не различающийся между версиями каталог ограничений.

Запрос: db/hub-schema-snapshot.sql. Снимок без пользовательских строк: docs/checks/2026-10-22-hub-schema.json. Повтор: node scripts/local-schema-snapshot.mjs && node scripts/compare-hub-schema.mjs.

## Параллельные запросы

scripts/local-engine-http-check.mjs запускает настоящий POST-обработчик app/api/tournament-engine/route.ts через локальный HTTP-сервер и существующий hub_engine_commit в изолированной PostgreSQL. Доступ пользователя подставлен тестовым адаптером; транспорт Supabase Auth не имитируется как прошедшая приёмка.

- 12 одновременных уникальных запросов с одной версией: 1 HTTP200, 11 HTTP409; одна новая ревизия и одна запись аудита.
- 12 одновременных повторов с одним request_id/командой: все HTTP200; одна новая ревизия и одна запись аудита.
- Повтор ключа с другим payload: HTTP409.
- Чужой организатор: HTTP403.
- Фикстуры откатились, auth.users после отката пустая; hosted данные не создавались.

PGlite сериализует SQL одного подключения. Этот тест доказывает обработку конкурирующих HTTP-запросов и CAS/идемпотентность реального SQL, а не конкуренцию нескольких hosted DB-сессий. Этот предел проверки сохранён явно. Полный hosted путь игрока/капитана/организатора остаётся отдельным незавершённым пунктом.
